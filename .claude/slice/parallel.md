# Parallel slices
Read by `/slice` when it offers or orchestrates parallel sessions; never in auto mode (the loop starts the next run itself).

**A round that should run by itself runs in the script, not in a chat:** `python .claude/scripts/slice_loop.py --parallel --yes` in a terminal of its own. A chat cannot drive a round: a desktop harness refuses to start a session on a turn a background event started and turns it into a card someone has to click, reports of finished sessions can wait until the user writes, and compaction takes these rules out of the chat's context. So when the user asks for an automatic or unattended round, give them this command instead of orchestrating, and propose no slices as cards. The script parks a slice with an open decision or a failure and goes on with the others. In a chat, read `.slice-loop/slice-NN.parked` (the reason) and `.slice-loop/events.jsonl` (the history), and write the user's answer to `.slice-loop/slice-NN.answer`; the next start of the script builds that slice.

A chat next to the script keeps the user informed: right after giving them the command, start `python .claude/scripts/slice_loop.py --notify` as a background command. It ends when a slice has a problem or a question and prints `SLICE-PROBLEM: NN …` or `SLICE-QUESTION: NN …`; its end wakes the chat. Tell the user at once in plain words what the slice needs, ask a question exactly as it stands, write their answer to the named file and tell them to start the script again once it has finished. Then start `--notify` again; also after `SLICE-NOTIFY: no problem after …`. After `SLICE-NOTIFY: no open round` stop. Finished slices stay out of the chat: they are in the Slice Board, and every report in the chat costs a turn.

The rest of this file is for slices the user wants to steer themselves.

Ready = not done, no branch slice-NN, every slice in "deps" done. When two or more slices are ready (not counting the one this session works on), offer one separate session per ready slice, unasked and once per run.
- Offer, never start unasked: list the ready slices with name and kind (app, web, docs), name the ones that share a file (field "files" in work/_slices.json: equal paths or a folder prefix; registration files such as the shell, the app's resource list or a route table count) – those run one after the other, and a slice that builds a scaffold others use lands first –, suggest at most two at once (three sessions on one machine made unrelated tests red under load and queued at the full-suite lock), and ask which ones to start.
- On a yes, start each chosen slice in its own session in this repository's main checkout, with your harness's tool for separate sessions if it has one (sharing this checkout, not a worktree of the harness: the slice creates its own worktree), on the slice's model: the field "model" of its entry in work/_slices.json goes into that tool's model parameter, never the model of this session. Without such a tool, print one ready-to-paste prompt per slice instead, each headed by the command line that starts it: `claude --model <model of the slice>`.
- A session cannot start a session on a stronger model than its own: the tool silently falls back. So the orchestrating session (the one that only dispatches and squashes) runs on `opus` at low effort – the strongest tier any slice may name, cheap because it writes no code. After each start, check the model it actually runs on with the harness's session tool and switch it to the slice's model when it differs.
- Each prompt is short: the line "/slice NN parallel auto", then the slice's goal and acceptance cases from work/_slices.json in a few lines, and one line with the facts a hook asks for before a session's first command or edit (the request in one sentence, what the command checks) when the repository runs such a hook. When the tool asks for a background text, give two or three sentences: round, slice, branch slice-NN, what done looks like. Nothing else is pasted: the command reads the rest itself and ends with SLICE-READY: NN or SLICE-WAIT; the squash happens in the main checkout through the merge queue (`slice_loop.py --merge`) or the running loop.
- Right after starting sessions, the orchestrating session starts `python .claude/scripts/slice_loop.py --merge --watch` as a background command: it waits for a slice to report ready, squashes, and its end wakes the chat, also when a session's own report does not arrive (two slices once waited four hours). When it ends, start the next slices and the watch again.
- `slice_loop.py --merge` squashes the ready slices. Add `--verify` – the full check chain once on the integration branch – as the check level asks (/slice section 4, step 1): at the round's milestones on level 3, after every group on levels 4 and 5; round close runs the chain on every level.- The orchestrating session acts only on SLICE-READY (run the queue), NEEDS-DECISION (ask me) and SLICE-OPEN (look at the reason). A SLICE-WAIT, or any other turn end without one of these markers, gets no answer and no status line: end the turn without text. `--merge` lists a slice whose session has not reported ready yet as "not ready yet" and still exits 0; a non-zero exit means a slice was left behind for a real reason.
- Never two sessions on one slice: a slice with a branch slice-NN is in progress, not ready.
